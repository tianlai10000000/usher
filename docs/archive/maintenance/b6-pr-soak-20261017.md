## Diagnostic evidence and candidate

The original B5 intrusive 900-second diagnosis reproduced allocator residency
growth while exact live heap bytes remained nearly flat. Separate lite stack
logging showed only 39,024 bytes of net live growth between two snapshots;
its largest growing stacks ended in macOS OpenGL/Core Animation/libdispatch
presentation. The stack-logging run changes allocation layout and execution
speed; neither it nor the intrusive snapshots are formal P6 results.

Repeated session resets also repeatedly rebuild builtin SyntaxSet/Theme and
their lazy grammar/regex state. B6 tests this mechanism by retaining one builtin
resource graph per controller, independently of session leases. It leaves
source preparation, per-file parsing, workload, cancellation and completion
identity unchanged. A single graph is not a byte-size bound; closed-review
memory retention is part of the required verification.

Closed diagnostic evidence is preserved under
`docs/validation/b6-pr-soak-20261017/diagnosis/`. The controlled B5/B6 900-second
comparison and original A/B6 three 90-second AB/BA/AB pairs are complete.
Complete P6 and its four soaks were **not executed for rejected B6**. Their
execution remains required for a subsequent candidate.

## Native launch diagnostics

The first attempted launch found the desktop locked and started no application.
After manual unlock, two private frontguard versions rejected the idle Apple
`spindump` service before creating a workload directory or starting an app.
Version 1 classified by basename alone; version 2 also compared an intermediate
BSD `ps` column that was truncated to `/usr/sbin/spindu`. Both failures and
their scripts remain preserved. Correcting that diagnostic distinction does
not modify Release settings, workload or performance acceptance thresholds.
The temporary preparation awake guard is stopped before native measurement.

Version 3 validates the complete executable from the inventory's final column
and the complete argv from a separate final-column query. The exception requires
root UID, launchd parent, bare `/usr/sbin/spindump` argv, observed CPU `0.0`, and
the exact trusted Apple service plist. A real read-only production check and
20 positive/negative tests passed. This is an idle OS-daemon point observation,
not a guarantee against future OS activity. All three versions remain archived.

## Root-cause conclusion and rejection

The repeated builtin graph teardown/reinitialization is a demonstrated
contributor to this workload's allocator-residency growth: exact code/workload
is preserved, resource loads fall from 775 to 1, and RSS growth/slope pass under
the single lifecycle intervention. Live heap/stack evidence does not establish
a growing business-object leak or identify every allocator page's owner.
The finite single B5-then-B6 order remains a causal-evidence limitation.

Keeping the graph for the controller's entire lifetime introduces an additional
closed footprint cost, so **B6 is rejected and may not become the next accepted
baseline**. A follow-up must preserve reuse across immediate resets while
releasing genuinely idle resources. It must repeat original-A controlled
acceptance, complete P6 and all four 900-second soaks under the same Release
parameters and thresholds. No allocator purge, workload reduction or gate change
was used. Full-source preparation was not moved as part of B6.

The [rejected runtime manifest](../../validation/b6-pr-soak-20261017/runtime-rejected/manifest.json)
preserves all eight native runs, raw audits, exact exits, frontend failures,
protocol versions and original templates. Its SHA-256 is
`a37bbef508e258ba473c417d423668cc153f04dcd5f3639b33b69948d7b58283`.
Original A, B3/B4/B5 results and the frozen B6 source/binary/build remain intact.
The old complete native UI matrix and physical Cmd-F were not rerun here.
