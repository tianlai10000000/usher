# Pull request workflow / Pull Request 工作流

## Scope / 范围

This specification is the portable contract for the current pull-request capability: project-scoped counts, the paginated PR/MR list, the full-window review workspace, diff/source enrichment, remote review, merge, and capability-gated revert commands, and the separate local recommendation flow.

本文是当前 Pull Request 能力的可迁移契约：项目级计数、分页 PR/MR 列表、全窗口审核工作区、diff/源码补全、远端评审、合并与按能力开放的回退命令，以及彼此独立的本地建议流程。

## Product boundary / 产品边界

The current product supports the following workflow:

1. A selected project optionally displays counts of open changes targeting `fat`, `uat`, and `prod`.
2. The PR tab loads one page of open, closed, merged, or all changes and displays number, title, branch pair, author, and UTC+08:00 update time. Branch and Updated cells wrap instead of using ellipsis; each row grows with the wrapped cell height so multi-line Branch pairs are not clipped. A horizontal scrollbar appears when the list card is narrower than the table floor width.
3. Opening a row navigates to a dedicated full-window PR review route with Conversation, Commits, and Files changed tabs (Checks is intentionally excluded). The Conversation timeline includes GitHub-style activity rows for commit batches and merges in addition to description/comments/reviews; adapters map provider-native sources into the shared kinds without sharing provider rules. Commit rows under a Conversation `commits` batch and the Commits tab list both render newest→oldest (latest change first), while UTC+08:00 date grouping on Commits still places newer calendar days above older ones. The tabs keep the product's underline selection style while using upstream GitHub Primer Octicons and inline icon/label/count geometry. Overall additions, deletions, and the five-cell diffstat live at the right edge of this primary tab row rather than being duplicated in the Files changed toolbar. Commits groups entries by UTC+08:00 calendar date in one shared GitHub-style card (Primer medium 6px corner radius with real border strokes, Box-row-like ~16px/12px internal padding, and a clear gap under the date heading), shows title, author, GitHub-style commit time (`yesterday`, `last week`, or past the 30-day Primer threshold `on Mar 19` / `on Mar 19, 2025`) with an absolute-datetime tooltip, verification state, and a vertically centered short SHA, and provides a tooltip-labeled full-SHA copy button while intentionally omitting the web page's code-browse button. Files changed provides the file tree, per-file Unified or Split diff, GitHub-style file actions, immutable base/head references, filtering, folder collapse, and next/previous file navigation.
4. The Files changed toolbar can open a GitHub-style commit selector and switch between the complete PR diff and a contiguous commit range. The selector reuses the newest→oldest Commits model; the controller maps selected display indices back onto the provider-neutral oldest→newest list before range selection. Provider adapters normalize commit collections from oldest to newest for that math. Selecting the chronologically first PR commit uses the PR base SHA; any later starting commit uses the preceding PR commit as the comparison base, so the first selected commit remains included. A single-commit selection adds one compact summary row to the Files changed toolbar with its title, previous/next commit navigation, author/time, short SHA, and full-SHA copy action. The summary starts exactly at the file-tree right divider, keeps its title left-aligned in the Diff region, and must not consume vertical diff space; the intentionally omitted Browse files action must not be added. Previously loaded ranges are cached for the active PR. The selected file toolbar can copy the file path, toggle between expanding all hidden lines and collapsing non-diff lines, or switch between the diff and the complete immutable file source. Hidden diff context can also be expanded in bounded 20-line increments.
5. The manual “Analyze PR” form produces a local risk recommendation; the user can record an approve/reject decision in the app state.
6. `Review changes` opens one GitHub-style dialog for Comment, Approve, or Request changes. The selected provider capability controls which choices are enabled, and submission writes to the remote provider. The Conversation tab also has a GitHub-style plain-text comment composer at the bottom (`Write` + green `Comment`) that submits the same Comment review action.
7. Review submission never merges automatically. After a successful review the controller refreshes remote action state; only a server-reported mergeable PR enables `Merge pull request`, whose confirmation dialog offers only provider/repository-supported methods and optional source-branch deletion. A successful review or merge invalidates the cached Conversation timeline and reloads it immediately when Conversation is the active tab, so remote review and merged activity are visible without switching tabs.
8. A merged PR hides review and merge controls. When the adapter reports a safe server-side revert capability, the header exposes a visible secondary revert button and a provider-specific confirmation. GitHub creates a separate revert PR. Gitee Enterprise writes a revert commit directly to the target branch only when the PR has a merge/squash commit and `GET /projects/:id/repository/commits/:sha/refs` reports both `merge_commit_by_pr=true` and `can_revert=true`; rebase and fast-forward merges remain unavailable. Public Gitee and GitLab do not expose this command.

The local recommendation remains a deterministic local rule, not an LLM call or CI/code-scanning integration. Close/reopen, inline draft reviews, merge queues, and auto-merge are not part of the current command set.

当前产品支持以下以只读为主的流程：

1. 选中项目后，可选显示目标为 `fat`、`uat`、`prod` 的 open 变更数量。
2. PR Tab 加载 open、closed、merged 或 all 的一页变更，显示编号、标题、分支对、作者和东八区更新时间。Branch 与 Updated 列换行完整显示，不得使用省略号；行高随换行内容增高，避免多行 Branch 被裁切；列表卡片窄于表宽下限时出现横向滚动条，而不是丢列。
3. 打开某一行后导航到独立的全窗口 PR 审核路由，提供 Conversation、Commits、Files changed Tab（明确不包含 Checks）。Conversation 时间线除描述/评论/Review 外，还包含 GitHub 风格的批量提交与合并活动行；各 adapter 把 Provider 原生数据映射到共享 kind，不共享彼此判定规则。Conversation 中 `commits` 批次下的提交行与 Commits Tab 列表均按从新到旧展示（最新变更在前），Commits 按东八区自然日分组时较新的日期仍排在较旧日期之上。Tab 保留产品的下划线选中样式，但使用 GitHub Primer 官方 Octicon 及同行的图标/文字/计数布局。全局增删行数与五格 diffstat 放在主 Tab 行右侧，不再重复显示在 Files changed 工具栏。Commits 按东八区自然日分组到同一个 GitHub 风格卡片中（Primer medium 6px 圆角使用真正的 border 描边，行内约 16px/12px 内边距，日期标题与卡片之间留出空隙），显示标题、作者、GitHub 风格相对提交时间（如 `yesterday`、`5 days ago`、`last week`）及绝对时间 Tooltip、签名状态和垂直居中的短 SHA；每行提供带 Tooltip 的完整 SHA 复制按钮，但明确不提供网页最右侧的代码浏览按钮。Files changed 展示文件树、按文件的 Unified 或 Split diff、GitHub 风格文件操作、固定的 base/head 引用、筛选、目录折叠与上/下一个文件导航。
4. Files changed 工具栏可打开 GitHub 风格的 commit 选择器，在完整 PR Diff 与连续 commit 范围之间切换。选择器复用 Commits 的从新到旧展示 model；控制器在计算范围前把选中的展示索引映射回 Provider-neutral 的从旧到新列表。Provider adapter 仍把 commit 集合归一为从旧到新以供该计算使用。范围从时间线上第一个 PR commit 开始时使用 PR base SHA；从后续 commit 开始时使用其前一个 PR commit 作为比较基准，因此不会漏掉首个选中 commit。单 commit 状态把标题、前后 commit 导航、作者/时间、短 SHA 和完整 SHA 复制操作压缩成一行；该行从文件树右侧分隔线的位置准确起始，标题在 Diff 区域内左对齐，不额外占用垂直空间；明确不加入 Browse files。已加载范围在当前 PR 内缓存。选中文件工具栏支持复制文件路径、在“展开全部隐藏行”和“收起非 diff 行”之间切换，以及在 diff 与固定提交的完整文件源码之间切换；方向展开按 GitHub 登录后的新版 `/changes/{commit}` 行为每次补充 21 个主侧源码行。
5. 手动填写的“Analyze PR”表单生成本地风险建议；用户可在应用状态中记录 approve/reject 决定。
6. `Review changes` 使用一个 GitHub 风格弹窗承载 Comment、Approve、Request changes；Provider 能力决定选项是否可用，提交会写入远端。Conversation Tab 底部另有 GitHub 风格纯文本评论框（`Write` + 绿色 `Comment`），提交同一 Comment 评审动作。
7. 评审成功后不会自动合并。控制器会刷新远端 action state；只有服务端报告可合并时才启用 `Merge pull request`，确认弹窗只列出 Provider/仓库允许的策略，并可选择删除源分支。Review 或 merge 成功后必须使 Conversation 时间线缓存失效；如果当前正处于 Conversation Tab，则立即重新加载，使远端 Review 与 merged 活动无需切换 Tab 即可出现。
8. PR 已合并后隐藏评审和合并控件。只有 adapter 报告安全的服务端回退能力时，页头才显示明确可见的次级回退按钮，并展示 Provider 专属确认说明。GitHub 创建独立的反向 PR；Gitee 企业版仅在 PR 存在 merge/squash commit，且 `GET /projects/:id/repository/commits/:sha/refs` 同时返回 `merge_commit_by_pr=true` 与 `can_revert=true` 时，直接向目标分支写入回退提交；rebase 和 fast-forward 合并保持不可用。Gitee 公有版与 GitLab 不开放该命令。

本地建议仍是确定性规则，不调用 LLM，也不接入 CI 或代码扫描。当前命令集不包含关闭/重开、行内草稿评审、merge queue 或 auto-merge。

## Ownership / 职责

- `src/workflow/pr_review.rs` owns the active request, stale-response protection, remote action sequencing, one-entry diff cache, immutable-ref source cache, hunk expansion, and Slint model updates.
- `src/git/` owns provider-neutral diff models and provider-specific request/response handling.
- `src/codereview/api/` owns provider endpoint URL templates only.
- `ui/views/workflow/pr_review_workspace.slint` owns review layout and user interaction; `ui/main.slint` mounts it only for the dedicated `PrReview` route.
- `src/workflow/pr_list.rs` owns list-page selection, list request sequencing, pagination presentation, and UTC+08:00 timestamp formatting.
- `src/workflow/pr.rs` owns the local recommendation and manual-decision state; it has no provider write API.
- `src/workflow/bindings.rs` supplies the selected project context and the optional `fat`/`uat`/`prod` count refresh.
- `src/project/pr_stats.rs` owns the legacy blocking branch-count adapters; it is separate from the provider-neutral list/review façade.

- `src/workflow/pr_review.rs` 负责当前请求、旧响应防护、远端 action 序列、单项 diff 缓存、固定提交源码缓存、hunk 展开和 Slint model 更新。
- `src/git/` 负责 Provider-neutral diff 模型及各 Provider 的请求/响应处理。
- `src/codereview/api/` 只负责 Provider endpoint URL 模板。
- `ui/views/workflow/pr_review_workspace.slint` 负责审核布局和交互；`ui/main.slint` 只在独立的 `PrReview` 路由挂载它。
- `src/workflow/pr_list.rs` 负责列表页选择、列表请求序列、防止旧响应覆盖、分页展示和东八区时间格式化。
- `src/workflow/pr.rs` 负责本地建议和人工决定状态；它不拥有 Provider 写接口。
- `src/workflow/bindings.rs` 提供当前项目上下文并触发可选的 `fat`/`uat`/`prod` 数量刷新。
- `src/project/pr_stats.rs` 负责历史遗留的阻塞式分支计数适配；它与 Provider-neutral 的列表/审核 façade 分离。

## Portable domain contract / 可移植领域契约

An implementation in another stack should preserve these provider-neutral records rather than expose provider JSON to the UI:

| Record | Required fields | Notes |
| --- | --- | --- |
| `RepositoryContext` | project key, provider type, provider project id, remote URL | The persisted provider type must agree with the remote URL before any request is made. |
| `PullRequestPage` | items, total, `total_exact`, optional page count | The UI distinguishes an exact total from a lower bound. Page size is 10. |
| `PullRequestItem` | number, title, author, source branch, target branch, updated time, web URL | A missing branch is shown as `—`; parseable timestamps are rendered as `YYYY-MM-DD HH:MM:SS +08:00`. |
| `PullRequestDiffDetail` | files, added/removed totals, commit count, optional conversation count, base SHA, head SHA, start SHA, too-many-commits flag | The summary commit and conversation counts keep the lazy Commits/Conversation tab badges accurate before those tab payloads load. Commit-range compares leave `conversation_count` unset so they cannot wipe the PR-level badge. The SHA values are immutable source references for later context expansion. |
| `PullRequestDiffFile` | path, old path, change type, added/removed counts, lines | Change types are `new_file`, `deleted_file`, `renamed_file`, or `edit_file`. |
| `PullRequestDiffLine` | old line, new line, kind, content | Kinds are normalized to hunk/context/addition/deletion before rendering. Content is one visual source line and contains no CR/LF controls. |
| `PullRequestConversationItem` | id, kind, author, optional avatar URL/author association, body, created time, state | Description, comments, reviews, and provider system events share one chronological presentation model. GitHub review responses expand into an atomic `review_summary` + optional `review` card pair; state controls the semantic wording (`commented`, `approved these changes`, or `requested changes`) and `AUTHOR` controls the Author badge. Relative time follows GitHub Primer `<relative-time>` defaults (`yesterday`, `last week`, or past `P30D` `on Mar 19` / `on Mar 19, 2025`) and remains inline with the event text; absolute time stays in a tooltip. A merged event suppresses the redundant closed event emitted for the same merged PR. GitHub, GitLab, and both Gitee profiles normalize provider and commit-author avatar fields; the controller downloads bounded avatar payloads off the event loop, while the UI falls back to an author initial. Description/comment/review cards and the composer share the same 52 px avatar/content grid. Timeline connectors are computed between semantic neighbors: a terminal merge stops its rail, while consecutive `review_summary` + `review` pairs retain one continuous rail between the preceding card and the next summary marker. Conversation body text is decoded inside each provider adapter: GitHub/GitLab use `body`; Gitee public v5 prefers `body`; Gitee Enterprise reads `note`, then `body`/`comment`, then string `content` only (object `content` is diff context). Enterprise may also best-effort merge `/reviews` without replacing note cards. Structured activity kinds `commits` / `commit` / `merged` / `event` render GitHub-style rows. A `commits` header and its consecutive `commit` children form one atomic sorting block; the children render newest→oldest. |
| `PullRequestCommit` | SHA, title/message, author, authored time, verified | Commit signatures are shown only when the provider reports verification. |
| `PullRequestActionState` | review/revert capabilities, normalized readiness kind/detail, review state, mergeable flag, merge/revert block reasons, revert label/confirmation, allowed merge methods | The UI renders normalized capabilities and provider-specific effect text; it never infers merge or revert safety from provider names. |
| `PullRequestReviewAction` | Comment, Approve, Request changes | A provider may disable unsupported actions but labels remain consistent. |
| `PullRequestMergeMethod` | Merge, Squash, Rebase, Fast-forward | Only methods returned by the active adapter are selectable. |

其他技术栈应保留这些 Provider-neutral 记录，而不是向 UI 暴露 Provider JSON：

| 记录 | 必需字段 | 说明 |
| --- | --- | --- |
| `RepositoryContext` | 项目 key、Provider 类型、Provider 项目 ID、remote URL | 每次请求前，已持久化的 Provider 类型必须与 remote URL 一致。 |
| `PullRequestPage` | items、total、`total_exact`、可选 page count | UI 区分准确总数和下界；每页固定 10 条。 |
| `PullRequestItem` | 编号、标题、作者、源分支、目标分支、更新时间、网页 URL | 缺失分支显示 `—`；可解析时间显示为 `YYYY-MM-DD HH:MM:SS +08:00`。 |
| `PullRequestDiffDetail` | 文件、增删总数、提交总数、可选会话计数、base SHA、head SHA、start SHA、过多提交标记 | 摘要提交数与会话数让 Commits/Conversation 列表尚未懒加载时也能显示准确徽标；commit-range 比较不设置 `conversation_count`，避免覆盖 PR 级徽标；SHA 是后续展开上下文所用的固定源码引用。 |
| `PullRequestDiffFile` | 路径、旧路径、变更类型、增删统计、行 | 变更类型归一为 `new_file`、`deleted_file`、`renamed_file`、`edit_file`。 |
| `PullRequestDiffLine` | 旧行号、新行号、类型、内容 | 在渲染前归一为 hunk/context/addition/deletion；内容必须是一个不含 CR/LF 控制符的视觉源码行。 |
| `PullRequestConversationItem` | id、类型、作者、可选头像 URL/作者关联、正文、创建时间、状态 | 描述、评论、Review 和 Provider 系统事件共用一个按时间排序的展示 model。GitHub Review 展开为不可拆分的 `review_summary` + 可选 `review` 卡片；state 决定 `commented`、`approved these changes`、`requested changes` 话术，`AUTHOR` 决定 Author 角标。相对时间遵循 GitHub Primer `<relative-time>` 默认（`yesterday`、`last week`，超过 `P30D` 则为 `on Mar 19` / `on Mar 19, 2025`），与事件文字同行，绝对时间放在 Tooltip；已合并 PR 的 `merged` 事件会抑制同一操作产生的冗余 `closed` 事件。GitHub、GitLab 与两种 Gitee profile 归一化头像字段；控制器在 event loop 外下载有大小上限的头像。时间线连接线由相邻事件语义计算：merge 终止轨道；连续的 `review_summary` + `review` 对之间，从前一张卡片到下一条 summary 标记必须保持一条连续轨道。评论文本由各 Provider adapter 解码：GitHub/GitLab 使用 `body`；Gitee 公有 v5 优先 `body`；Gitee 企业版依次读取 `note`、`body`/`comment`、字符串 `content`。企业版可尽力合并 `/reviews`，且不得覆盖已有 note 卡片。`commits` 头及其连续 `commit` 子项构成不可拆分的排序块；子项按从新到旧展示。 |
| `PullRequestCommit` | SHA、标题/正文、作者、提交时间、verified | 只有 Provider 明确返回签名验证时才展示 Verified。 |
| `PullRequestActionState` | 评审/回退能力、归一化就绪类型/详情、评审状态、可合并标记、合并/回退阻塞原因、回退标签/确认说明、允许的合并策略 | UI 只渲染归一化能力和 Provider 专属效果说明，不得根据 Provider 名称自行推断合并语义或回退安全性。 |
| `PullRequestReviewAction` | Comment、Approve、Request changes | Provider 可禁用不支持的动作，但显示标签保持一致。 |
| `PullRequestMergeMethod` | Merge、Squash、Rebase、Fast-forward | 只能选择当前 adapter 返回的方法。 |

## Provider adapter contract / Provider 适配契约

Provider adapters accept a validated `RepositoryContext` and return only the domain records above. They own provider URLs, authentication headers, pagination interpretation, JSON decoding, and normalization. The UI and workflow controller neither construct URLs nor parse provider JSON.

| Provider | Read path | Review | Merge | Authentication | Tab badge counts |
| --- | --- | --- | --- | --- | --- |
| GitHub / GitHub Enterprise | issue search plus visible-row detail; PR files and contents | Comment, Approve, Request changes | repository-enabled Merge, Squash, Rebase | `Authorization: Bearer <token>` | Commits from detail `commits` or one `per_page=1` probe via Link `rel=last`; Conversation is detail `comments` plus the independently counted reviews collection, because COMMENT reviews are excluded from `comments` |
| GitLab | MR list/detail/diffs/raw file | not implemented | not implemented | `PRIVATE-TOKEN` when configured | Detail `commits_count` / `user_notes_count`; if commit total missing, one `per_page=1` commits probe via `X-Total` |
| Gitee public v5 | repository pull list/detail/files/contents | Comment only; v5 has no approve/request-changes endpoint | Merge, Squash | public Gitee token via `Authorization: token` | Detail `commits`/`commits_count` and `comments`/`comments_count` when present; otherwise one bounded `per_page=100` commits/comments probe (`len < per_page` is exact). Never cache full Conversation/Commits payloads for badges. |
| Gitee Enterprise v8 | project MR list/diff/file and `current_state` | Conversation Comment uses `POST /notes` with `note` and required `noteable_type: PullRequest`; Approve/Request changes use `/reviews` with `approved`/`rejected` | `restrict_merge_type`: Merge, Squash, Rebase, Fast-forward | enterprise header, `OAUTH: enabled`, separate enterprise `PRIVATE-TOKEN` | Conversation from MR detail `user_notes_count`/`notes_count`; a positive Commits count may come from diffs `commits_size` (not file-total `count`), a non-truncated embedded `commits` array, or detail. Zero is not authoritative because some deployments advertise zero before the collection is read; zero/missing first probes `with_page=true&per_page=1` for a total. A total-less response whose length equals `per_page` is ambiguous even when it is a bare array; retry the documented `with_page=false` complete collection, count it, and discard it without mounting the lazy Commits content model. |

GitHub list search provides an exact total but not `head.ref`/`base.ref`. Its extra detail requests are limited to the visible page; a failed row enrichment must not discard the page. GitLab and Gitee may report totals through headers or provider contracts; when an exact total is absent, the paginator shows a lower bound and permits the next page after a full response.

Revert is a separate capability from merge. GitHub uses the GraphQL `revertPullRequest` mutation and returns the new reverse PR. Gitee Enterprise first reloads the MR, then calls the documented commit `/refs` endpoint; only its `merge_commit_by_pr` plus `can_revert` pair permits `POST /projects/:id/repository/commits/:sha/revert` with the target `branch_name`. The latter mutates the target branch immediately and therefore uses different confirmation text. No adapter reconstructs a commit range locally.

Provider 适配层接收已验证的 `RepositoryContext`，只返回上述领域记录。它负责 Provider URL、鉴权 header、分页解释、JSON 解码和归一化；UI 和 Workflow controller 均不构造 URL，也不解析 Provider JSON。

| Provider | 读取路径 | 评审 | 合并 | 鉴权 | Tab 角标计数 |
| --- | --- | --- | --- | --- | --- |
| GitHub / GitHub Enterprise | issue search + 可见行详情、PR files、contents | Comment、Approve、Request changes | 仓库启用的 Merge、Squash、Rebase | `Authorization: Bearer <token>` | Commits 使用 detail `commits` 或一次 `per_page=1` + Link `rel=last` 探测；Conversation 为 detail `comments` 加独立计数的 reviews 集合，因为 COMMENT review 不计入 `comments` |
| GitLab | MR list/detail/diffs/raw file | 暂未实现 | 暂未实现 | 已配置时使用 `PRIVATE-TOKEN` | Detail `commits_count` / `user_notes_count`；缺提交总数时用一次 `per_page=1` commits 探测（`X-Total`） |
| Gitee 公有 v5 | 仓库 PR list/detail/files/contents | 仅 Comment；v5 无 approve/request-changes endpoint | Merge、Squash | 公有版独立 token，使用 `Authorization: token` | Detail 有 `commits`/`commits_count`、`comments`/`comments_count` 时优先；否则各发一次有界 `per_page=100` commits/comments 探测（`len < per_page` 即为精确总数）。角标不得缓存完整 Conversation/Commits 载荷 |
| Gitee 企业 v8 | project MR list/diff/file 与 `current_state` | Conversation Comment 使用 `POST /notes` + `note` + 必填的 `noteable_type: PullRequest`；Approve/Request changes 使用 `/reviews` + `approved`/`rejected` | `restrict_merge_type` 返回的 Merge、Squash、Rebase、Fast-forward | enterprise header、`OAUTH: enabled`、企业版独立 `PRIVATE-TOKEN` | Conversation 用 MR detail 的 `user_notes_count`/`notes_count`；Commits 正数可取自 diffs 的 `commits_size`、未截断的内嵌 `commits` 数组或 detail。部分部署读取集合前会报告零，因此零值不作为可信总数；零值或缺失时先用 `with_page=true&per_page=1` 探测。无 total 且返回数量等于 `per_page` 时，即便载荷是裸数组也无法判定完整性；必须回退读取文档约定的 `with_page=false` 完整集合，计数后立即丢弃，不得挂载懒加载 Commits 内容 model。 |

GitHub 搜索列表提供准确总数，但不含 `head.ref`/`base.ref`。额外详情请求只限于当前可见页；单行补全失败不得丢弃整页。GitLab 和 Gitee 可通过 header 或 Provider 契约给出总数；没有准确总数时，分页器显示下界，并在满页响应后允许进入下一页。

回退是独立于合并的能力。GitHub 使用 GraphQL `revertPullRequest` mutation，并返回新建的反向 PR。Gitee 企业版先重新读取 MR，再调用文档定义的 commit `/refs` endpoint；只有其 `merge_commit_by_pr` 与 `can_revert` 同时为 true，才允许携带目标 `branch_name` 调用 `POST /projects/:id/repository/commits/:sha/revert`。后者会立即修改目标分支，因此确认说明必须与 GitHub 不同。任何 adapter 都不得在客户端自行重建 commit 范围。

## Execution and state flow / 执行与状态流

```text
project selected
  -> load persisted RepositoryContext off the UI thread
  -> validate provider type against remote URL
  -> fetch the selected list page through one provider adapter
  -> normalize records and apply only if list sequence is current
  -> user opens a row
  -> fetch normalized diff and remote action state with independent stale-response sequences
  -> cache one shared immutable base by project + request + whitespace mode
  -> build a local file tree and select/highlight the first file
  -> optional hunk expansion fetches immutable source once, then creates or mutates only that file's copy-on-write override
  -> collapse drops that override and exposes the provider-normalized base file without another request
  -> submit an explicit remote review command
  -> refresh action state after provider success
  -> when the provider reports mergeable, confirm one allowed method and send a separate merge command
  -> when a merged request reports can-revert, confirm the provider-specific effect and send a separate revert command
```

Every asynchronous boundary needs a monotonically increasing request sequence (separate sequences for list, conversation, commits, diff, syntax highlighting, and hunk expansion are recommended). A result may update the visible state only if its sequence, selected project, selected PR, and selected file still match. Closing the review or switching projects invalidates all in-flight work and clears review caches. Never let a stale result navigate back to the review route or replace a newer page.

```text
选择项目
  -> 在 UI 线程外读取持久化的 RepositoryContext
  -> 校验 Provider 类型与 remote URL
  -> 通过一个 Provider adapter 获取当前选中的列表页
  -> 归一化记录，且仅在列表序列仍为最新时回写
  -> 用户打开某一行
  -> 使用相互独立的旧响应序列获取归一化 diff 与远端 action state
  -> 按项目 + 请求 + 空白模式缓存一份共享且不可变的基础数据
  -> 构建本地文件树，选择并高亮第一个文件
  -> 可选的 hunk 展开只获取一次固定源码，再只创建或修改该文件的写时复制 override
  -> 收起操作删除该 override 并重新使用 Provider 归一化后的基础文件，不发起新请求
  -> 提交显式的远端评审命令
  -> Provider 成功后刷新 action state
  -> Provider 报告可合并时，确认一种允许的策略并发送独立 merge 命令
  -> 已合并请求报告可回退时，确认 Provider 专属效果并发送独立 revert 命令
```

每个异步边界都需要单调递增的请求序列（建议列表、Conversation、Commits、diff、语法高亮和 hunk 展开各自独立）。只有当序列、当前项目、当前 PR 和当前文件仍匹配时，结果才可更新可见状态。关闭审核或切换项目会使所有在途任务失效并清理审核缓存；旧结果绝不能重新导航回审核路由或覆盖新页。

5. 选择变更文件时只替换当前可见的行 model，不重复请求 diff。
6. Files changed 工具栏只提供一个 GitHub 风格的 `Diff view` 弹层。Unified/Split 与 Hide whitespace 在点击 `Apply and reload` 前均为草稿选择。Unified/Split 与 Provider 无关，只改变本地行投影；Split 会把每个连续增删块按行配对，并把上下文同时放到左右两侧。即使一侧为空，左右栏也必须保持等宽；长行只在各自栏内换行，左右单元格共享换行后的行高。Unified 长行也必须像 GitHub 一样在代码栏内换行，不得截断。Diff 源码使用已注册的 SF Mono、13px 字号和 22px 行高；普通 hunk 行为 28px，同时提供上下两个方向操作的 hunk 间隔行为 52px。Split 每侧使用绝对定位的 50px 行号栏（水平居中）及 20px 增删标记栏；Unified 的左右两个 50px 行号栏使用相同的绝对定位 Text 几何，使旧/新行号像 GitHub `.new-diff-line-number` 一样对称居中。换行后行号、增删标记和较短一侧的内容都固定在首个视觉行；`+`/`-` 不得按整条换行后的总高度垂直居中。行号与源码使用同一个普通文本渲染器以保持基线一致。变更行号使用正常深色前景，未变更行号保持 muted。可展开 hunk 的操作区只能占用对应行号栏：Unified 将左右两个 50px 行号栏合并为 100px，并把 Primer fold 图标水平居中；Split 仍使用单侧 50px gutter 居中。文件开头的隐藏区使用 Primer `fold-up-16`。hunk 间隐藏范围大于一页（21 行）时分别显示 `fold-down-16` 和 `fold-up-16`；剩余不超过一页时切换为 GitHub 的单个 `unfold-16` 全部展开操作。补齐最后上下文后必须移除 hunk 分隔行，不能留下空蓝行。SVG 必须原样采用当前 Primer Octicons 官方仓库文件。Hide whitespace 仅在当前 Provider endpoint 支持时启用（目前仅 Gitee 兼容企业版）；其他 Provider 仍显示但禁用复选框，且不得收到无效的空白字符请求。弹层使用 Primer 向上三角箭头（45° 描边/填充方块衔接顶边），尖端对准设置齿轮；面板被边缘夹紧时箭头仍跟随按钮。
7. 归一化 Diff 达到平台无关的大文件行数或载荷预算时，仍显示正常文件头和统计，但默认不创建语法 token 与 Slint 行 model。正文按 GitHub 显示 `Load diff` 和 `Large diffs are not rendered by default.`；点击后在原位显示 spinner，并且只渲染这个文件。显式加载状态在当前完整 Diff/commit range 内保留，切换 commit range 后重置。
7. Token、鉴权 header 和响应正文不得写入日志。
8. 审核工作区发送显式 Provider review 命令，只有 Provider 接受后才显示成功；独立的 Analyze/Approve/Reject 表单仍仅更新本地状态。
9. 左侧导航按路径组织变更文件，支持目录折叠和不区分大小写的路径筛选；选中筛选结果时仍使用 Provider 原始文件索引。文件状态 Octicon 使用 Primer 语义前景色：新增为 success、删除为 danger、重命名为 attention、修改为 muted，并分别适配浅色和深色值。GitHub 风格筛选菜单显示带本地计数的扩展名，可分别勾选扩展名，并提供 `Only manifest files` 限制和 `Viewed files` 可见性开关。`Files changed` 工具栏提供 GitHub 侧栏开关：隐藏文件树时同时移除分隔线和拖拽命中区，让 Diff 占满工作区；再次显示时恢复先前宽度。审核区宽度越过 Primer `$width-md`（768px）向下时自动折叠文件树、向上时自动展开——临界值对齐 GitHub `Layout--flowRow-until-md` + `sidebarPosition-flowRow-none` 在 `max-width: 767.98px` 下隐藏侧栏的规则。工具栏开关在任意宽度下都可手动切换，因此窄屏自动收起后仍可点开。主窗口最小宽度保持在该临界值之下（640px），确保阈值可到达。文件树和 Diff 行采用虚拟化，只实例化可见 delegate；分隔线随指针实时调整宽度，最小宽度 220 px、绝对最大宽度 520 px，并且动态上限为审核区宽度的 45%。macOS 原生 live resize 期间，工作区保持上一次稳定的内部几何尺寸，每条可见的非 hunk 代码行只渲染一个纯等宽文本节点；松开窗口边缘后只应用一次最终尺寸，并恢复按 token 着色的语法文本。
10. 文件筛选和上一项/下一项导航只操作本地 model，不得重新加载 diff 或增加 Provider 请求。
10.1. 打开 commit 选择器时按需复用 Provider-neutral PR commit 列表。保存 `All commits` 直接恢复原始缓存且不发网络请求；保存连续范围时，通过 Provider 仓库 compare endpoint 比较所选起点之前的 commit（或 PR base SHA）与所选终点。切换范围会失效高亮/源码缓存，旧范围响应不得覆盖较新的选择。
11. 归一化后的 `viewed` 字段驱动本地 `Viewed files` 筛选；若某 Provider 的同名字段语义不同，adapter 必须将其归一化为 `false`，不得把该 Provider 字段冒充审核进度。
12. 语法高亮由 Rust 使用 `syntect` 并根据当前文件路径生成；Slint 只接收带样式的 token model，不解析源码语言。Files changed 代码栏支持 GitHub 风格拖拽选中（Unified/Split），无需单独进入选择模式：选区几何使用实测等宽字符步进与显示列（含 Tab 和双宽字符），换行时只绘制实际命中的视觉片段，行号栏与 `+`/`-` 不在可选区域内。Hunk 头（`@@ … @@`）与 meta 行不可选中，且不会出现在 ⌘/Ctrl+A 选区或剪贴板文本中，行为与 GitHub 一致。Diff Flickable 不得仲裁指针拖动——代码区垂直拖动始终属于选中手势，滚轮/触控板与滚动条仍可滚动。跨行选区以换行拼接纯文本并静默写入剪贴板；⌘/Ctrl+A 选中完整 Unified diff 或当前 Split 侧，Escape 清除选区。切换文件、Tab、Diff view 或 line-model revision 时清除选区。选中必须保留 ListView 虚拟化：不得创建整文件 TextInput 或重复 token model，选区矩形只存在于当前已选且可见的 delegate。
13. 高亮前将 Tab 按四列制表位展开；可见 token 和空白宽度使用当前等宽字体的实际测量值。最长的已展开代码行使用同一字体测量，该像素宽度同时驱动横向滚动范围和每行 Diff 背景，滚动到最右端不得露出未绘制区域；没有可测量行时才回退到显示列数（包括双宽中日韩字符）。
14. PR 列表、PR 详情/diff 和仓库源码请求必须按当前项目持久化的 `repo_type` 分发；分发层同时校验其与 `remote_repo` 一致，任何调用方都不得静默回退到其他 Provider。
15. 只有确实存在隐藏上下文时才显示可点击的 hunk 控件。每次方向点击最多展示 21 个主侧源码行，以 GitHub 登录后的新版 `/changes/{commit}` 页面为准；未登录时回退的经典 `/commits/{commit}` 页面采用不同的 20 行分页，不能反过来改变本工作区的交互基准。修改文件按固定 base/head SHA 懒加载两侧源码，并在有界隐藏区内做本地行对齐，展开边界处的 base 独有删除行和 head 独有新增行都不得丢失；新增/删除文件只读取其适用的一侧。源码在当前审核期间缓存。
16. 源码展开请求复用 diff 加载的旧响应防护；切换项目、关闭审核或打开其他 PR 后，迟到的源码响应不得修改当前 model。
17. PR 列表固定每页 10 条。切换状态时重置到第 1 页；切换页码时只请求该页，GitHub 为可见行补充分支的详情请求除外。
18. Provider 时间戳若为有效 RFC 3339，必须在展示前转换为东八区（UTC+08:00）。无法解析的值应原样展示，不能替换成误导性的时间。PR 审核路由中，页头摘要、Conversation 时间戳与 Commits Tab 行时间遵循 GitHub Primer `<relative-time>` 默认（`threshold=P30D`、`prefix=on`）：30 天内使用相对时间（如 `3 hours ago`、`yesterday`、`5 days ago`、`last week`）；超过阈值后改为绝对短日期（同年 `on Mar 19`，跨年 `on Mar 19, 2025`）。悬停 Tooltip 仍显示绝对本地时间（如 `Jul 15, 2026, 1:26 PM GMT+8`）。Commits 行格式为 `{author} committed {label}`，因此相对时间为 `committed yesterday`，绝对时间为 `committed on Mar 19`。描述/评论卡片与 commits 批次行的相对时间把 Tooltip 放在标签右侧，避免 ListView/卡片裁剪；其他 Conversation 时间戳保持原有位置。Workflow PR 列表仍显示绝对东八区时间。
19. 文件筛选、目录折叠状态、树构建、选中文件导航和语法高亮均是本地展示操作；它们不得重载 diff。
20. 当前 Analyze/Approve/Reject 控件只更新项目级本地 Workflow 状态，绝不能声称远端 Provider 已接受审核决定。
21. 不得记录 token、鉴权 header 或无边界的 Provider 响应正文。后台列表、diff、分支补全和源码请求必须静默；视图自身拥有行内 loading 和 error 状态。
22. 切换文件和展开 hunk 时，语法高亮期间必须保留当前已渲染代码 model，完成后再原子替换。切换文件在替换完成后重置代码 viewport；展开 hunk 保持当前 viewport，且不得闪现空白区域。
23. 文件工具栏按 GitHub 顺序排列：文件图标、路径、复制路径、双状态 `Expand all lines`/`Collapse non-diff lines`、增删统计、上一/下一文件和更多操作。前置文件图标与文件树使用同一套 Primer change-type Octicon 及语义色（`file-added` / `file-removed` / `file-moved` / `file-diff`）。所有图标必须垂直对齐并提供 Hover Tooltip。展开状态使用 `unfold` 图标；插入任意隐藏上下文后切换为 `fold` 图标，点击后恢复保留的原始 diff。更多菜单使用 GitHub 的眼睛 Octicon；其操作在应用内切换 `View file`/`View diff`，并始终按 diff 的固定 head SHA 读取源码，删除文件使用 base SHA。不得打开浏览器或读取可变分支 tip。
24. 审核缓存必须有内存上限：归一化 diff 只保留一份共享且不可变的基础数据；展开上下文只按文件保存写时复制 override，收起文件时必须删除该 override。最多保留 4 个 commit-range Diff、最近使用的 4 个 Diff 高亮文件和 3 个固定源码文本；完整文件的高亮 model 只存在于当前 UI model，不进入 Diff 高亮缓存。
25. 请求成功且列表为零条时，在与错误状态一致的 Vuetify 风格大图布局中显示 GitHub 风格、随筛选变化的标题和准确的 `0 total`；两种状态下的插画、标题、说明和可选操作必须作为同一视觉列水平居中。空数据使用内置 teamwork 插画；请求、鉴权和响应结构失败使用内置 connection 插画和 `Retry Request` 操作。Provider adapter 的技术错误写入日志，但不得伪装成空数据或原样暴露在 UI 中。
26. Gitee API profile 必须确定性选择：remote host 与已配置企业 API host 匹配时使用 v8 和企业版 Token；其他 Gitee remote 使用公有 v5 和公有版 Token，两套凭据不得互相 fallback。
27. Review 与 Merge 是两个独立命令。Approve 成功绝不能自动合并，只刷新服务端状态；只有最新状态为可合并时才启用 Merge，并且只列出 adapter 返回的策略。
28. Gitee 公有 v5 保持 GitHub 标签，但因接口只有评论能力，Approve 和 Request changes 必须禁用。Gitee 企业版的普通 Conversation Comment 是 merge-request note，必须提交到 `/notes` 并使用 `note` 字段；只有 Approve/Request changes 进入 `/reviews` 并映射为 `approved`/`rejected`。Approve 未填写 review summary 时必须省略可选的 `comment` 字段，而不是发送空字符串；部分企业版部署会拒绝后者。
29. 关闭工作区或切换项目必须使在途 diff、source、review state、review submit 和 merge 响应失效；远端 action 执行期间必须阻止重复提交。
30. 合并就绪状态只共享展示契约，不共享 Provider 判定逻辑。GitHub 映射 REST `mergeable`/`mergeable_state`；Gitee 企业版映射 v8 `current_state` 条件（其中 `conflict_result=true` 表示无冲突）；Gitee 公有版只使用 v5 自身的可合并字段；GitLab 映射 `detailed_merge_status` 并请求异步重算。在 GitLab 远端 review/merge 命令实现前，其就绪状态只读。标题旁可点击的就绪徽标使用 GitHub Primer 的 success/attention/danger/done 前景色，与 review、merge 按钮保持相同高度和垂直基线，并按带 leadingVisual 的 Primer Button 尺寸贴合标签（左右内边距 + 图标 + 间距）。其 Provider 详情浮层遵循 Primer Overlay（12px large 圆角、16px spacer-3 内边距、宽度随内容且上限约 320px）。宽屏贴右的徽标用 ActionMenu `align: end` 打开；紧凑页头徽标靠近左 gutter 时用 `align: start` 向右展开，保留页边距，且不暴露原始 JSON。当 `can_revert` 为真时，Usher 在同一行显示按标签宽度收缩的 Primer 次级按钮，而不是复刻 GitHub 的 kebab ActionMenu，以保证完整回退文案可读。摘要行与标题左边缘对齐，并按 GitHub 顺序展示 open/closed/merged 状态胶囊、作者、提交数量、目标分支、来源分支、来源分支复制操作，以及相对更新时间。宽屏页头在标题与完整分支名能放下时保持单行；标题单行放不下时换行而不是省略号，分支名芯片从不截断——摘要放不下时把分支段移到第二行。宽屏下标题占据可伸缩的中间列，就绪状态/Review/Merge 控件贴齐标题首行右侧（页头主轴必须保持 stretch；若写成 `alignment: start` 会把标题列压成零宽）。返回导航改为 36 px GitHub Primer 风格 IconButton，使用官方 `arrow-left` Octicon，仅 hover 显示底色，并用位于返回图标下方的 `Back to pull requests` Tooltip 代替过宽文字按钮和分隔线。该 Tooltip 保持下方弹出位置，但挂在审核页头层（不嵌在按钮内）并以高 z 绘制，避免被摘要行 Open 徽章或就绪/Review 控件遮挡；不修改 Material ToolTip 及其他功能 Tip。窄屏使用紧凑的顶部和底部留白，并把操作区、标题和摘要放入独立布局区，禁止互相覆盖。紧凑页头下就绪状态/Review/Merge 控件紧跟返回图标左对齐，与 GitHub 一致，不再靠右。标题无法在一行内完整显示时换成两行，而不是显示省略号；摘要实测宽度足够时保持一行，只有确实放不下时才把分支部分移到第二行。页头正文与 Workflow PR 列表统一使用 Hiragino Sans GB。
31. Commit 筛选采用连续范围模型：第一次点击选中单个 commit；点击已选范围之前或之后的 commit 时扩展范围，不得清空已有选择。点击已选范围端点时向内收缩一个 commit；再次点击唯一选中的 commit 时清空范围；点击范围内部的 commit 时保持范围不变，因为 Provider compare 契约无法表达中间带空洞的选择。
32. Commit 范围弹窗只固定标题栏和底部操作栏；All commits、上次 Review 状态、范围标题、加载/错误状态和 commit 行必须处于同一个滚动区域。Commit 行默认使用紧凑高度，只有标题换行时才按需增高；最后一行不显示分隔线。
33. 选中范围覆盖全部 commit 时，所有 Provider 都必须复用已加载的完整 PR Diff，不得再次发起等价的 compare 请求；单 Commit PR 选择唯一 commit 也属于这种情况。Compare 失败的技术详情只写日志，行内 UI 仅显示有边界、与 Provider 无关的错误说明。
34. Conversation、Commits、Files changed 和 Commit 选择弹窗中的加载失败统一使用 GitHub 中性的 Blank Slate 样式：默认页面背景、Alert Octicon、正常前景色的 `Uh oh!`、弱化的重新加载说明，以及带边框的紧凑次级 `Try again` 按钮。不得使用红色大标题或主色恢复按钮。
35. Conversation 时间线的 commit 标题/短 SHA，以及 Commits Tab 的 commit 标题/短 SHA，都作为应用内 commit detail 入口。点击后复用当前 PR 的 Files changed 页面，将 commit selector 原子地设为该 commit 的单项范围；如果 Commits 内容尚未加载，先在后台加载并按 SHA 定位，再应用范围。复制 SHA 操作保持独立，不得触发详情导航。Commits Tab 行背景在指针位于该行任意处（含标题、短 SHA、复制、相对时间、kebab）时保持淡底，因为子级 TouchArea 会抢走父级行 hover；标题下划线与短 SHA 高亮仍仅在指针落在对应控件上时出现，不得由行背景 hover 单独连带触发。标题 hover 时保持正常前景色，并按每一行换行后的实际字形使用文本原生下划线；不得变成强调蓝色，也不得用一个矩形横线贯穿整个标题块。短 SHA 默认是透明背景、无边框的纯文字；只有直接 hover 时才显示按文字宽度加内边距的 GitHub 风格圆角 control-hover 淡底（浅色 `#eaeef2` / 深色半透明，而不是与行底相同的 page `bg-muted`，以便在白底与行淡底上都可辨认），并在上方显示 `View commit details`。当 message 在标题之外还有 body 时，标题旁带边框的 muted kebab（展开时使用 Primer accent-muted 底色与强调色图标）仅内联展开/收起 body，不进入详情。展开互不排斥：展开一条不会收起其他已展开条目。只有标题（和短 SHA）打开详情——行背景与 kebab 不是导航目标。展开态遵循 GitHub 顺序：首行标题/kebab/SHA，其下为按换行高度贴合的 message body，再下为带头像的作者行（`{author} committed {relative}`），两者之间保留紧凑呼吸间距，且 body 不得与作者行重叠。Commits Tab 标题超出列宽时换行显示，不得用省略号截断；作者/时间行与行高随换行增高。相对时间与作者行同高、同用 Hiragino，并与 `committed` 保持基线对齐。Message 展开按钮必须跟随换行标题最后一个字形后的精确光标位置。收起时 SHA 与复制操作在完整“标题 + 作者”摘要区内垂直居中；展开时则在整个展开行内垂直居中。
36. 展开或收起 commit message 时必须保持当前 ListView viewport 与被点击控件的屏幕位置；实现应原位更新现有 model 行，不能替换整个 model。当前行以上内容保持不动，只允许后续行下移或上移。
37. 返回导航分为两层。从 Conversation 或 Commits 打开 commit 时创建审核页内返回点；审核页头 Back 必须先恢复准确的来源 Tab，而从 Workflow PR 列表直接进入的审核页则返回 Workflow。跨页面导航使用 Router 的 LIFO 历史栈，不再依赖单个 previous-route 槽位。从活动审核页打开设置、关于或其他路由时必须保留审核状态；在该页面执行 Back 后恢复同一个 PR 审核页及其当前下钻状态。

## Rewrite checklist / 重写清单

- Keep repository configuration (`provider type`, `provider project id`, `remote URL`) persistent and project-scoped; keep the list/review cache session-scoped and disposable.
- Split the implementation into UI, workflow/controller, provider adapters, HTTP/auth, and persistence layers. Only adapters know provider response shapes.
- Preserve the normalized records and error/loading states above as the cross-layer API. A web, mobile, or native UI can replace Slint without changing provider adapters.
- Treat remote reads as cancellable or sequence-guarded. Prefer cancellation where the target runtime supports it, but preserve the “latest request wins” rule either way.
- Use immutable base/head references for expanded source. Do not expand context from a mutable branch tip.
- Keep per-file highlighting and source contents cached only for the active review; invalidate on project switch, PR switch, close, or whitespace-mode change as appropriate.
- Model remote review, merge, and revert as explicit commands with their own capabilities, confirmation, stale-response protection, and error behavior. They are not extensions of the local manual-status control.

- 将仓库配置（`provider type`、`provider project id`、`remote URL`）持久化并按项目隔离；将列表/审核缓存视为可丢弃的会话状态。
- 将实现拆分为 UI、workflow/controller、Provider adapters、HTTP/auth 与持久化层；只有 adapter 知道 Provider 响应结构。
- 将上述归一化记录和 loading/error 状态作为跨层 API。Web、移动端或原生 UI 可替换 Slint，而无需改动 Provider adapter。
- 远端读取必须支持取消或请求序列防护。目标运行时若支持则优先取消，但无论如何都要保留“最新请求优先”的规则。
- 展开源码必须使用固定的 base/head 引用，不能从可变的分支 tip 展开上下文。
- 每文件的高亮和源码内容只缓存于当前审核；在项目、PR、关闭或空白模式切换时按需失效。
- 远端 review、merge 和 revert 必须建模为显式命令，拥有独立的能力、确认、旧响应防护和错误行为；它们不是本地 manual-status 控件的简单延伸。
